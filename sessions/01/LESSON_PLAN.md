## 핵심 설명 내용

### 칠판에 그릴 한 장

```text
GitHub 원격 저장소
       ↓ clone
내 PC 로컬 저장소 — branch: diagnostic/id
       ↓ 파일 수정
작업 내용 — commit(저장 시점 + 설명)
       ↓ push
GitHub 개인 브랜치 — PR(합쳐 달라는 검토 요청)
       ↓ review / merge
main
```

### 사용할 비유

- commit: 게임의 세이브 포인트. 다만 무엇을 저장했는지 메시지가 남는다.
- branch: 원본을 건드리지 않는 별도의 작업 레일.
- PR: 완성 파일을 던지는 것이 아니라, 변경 내용을 보여 주고 합쳐 달라고 요청하는 절차.
- 충돌: 두 사람이 같은 기준의 같은 부분을 다르게 바꿔 자동 선택할 수 없는 상태.

### 반드시 물어볼 질문

- 파일을 저장한 것과 commit한 것은 무엇이 다른가?
- commit했는데 GitHub에서 안 보인다면 무엇을 하지 않았을 가능성이 큰가?
- 왜 `main`에서 바로 수정하지 않는가?
- PR은 파일 업로드와 무엇이 다른가?

### 흔한 오해

- commit과 push는 같은 작업이다 → commit은 로컬 기록, push는 원격 전송이다.
- branch를 만들면 폴더가 자동으로 하나 더 생긴다 → 같은 작업 폴더에서 Git이 버전을 전환한다.
- PR을 만들면 자동으로 병합된다 → 검토와 병합은 별도 단계다.
- 충돌은 실수한 사람이 생겼다는 뜻이다 → 정상적인 병렬 작업에서도 생긴다.

## 개인 실습 과제

1. 수업 저장소를 Fork로 clone한다.
2. `diagnostic/<GitHub아이디>` 브랜치를 만든다.
3. README의 학생 실습 구역에 아래 네 줄을 추가한다.
   - 표시 이름 또는 교사가 배정한 번호
   - 만들고 싶은 게임 기능 한 가지
   - Git 경험: 처음 / 조금 / 사용해 봄
   - 오늘 이해한 Git 용어 한 가지와 설명
4. commit 메시지는 `docs: add <아이디> diagnostic` 형식으로 작성한다.
5. 브랜치를 push하고 PR을 만든다.
6. PR 본문에 `변경 내용`, `직접 확인한 것`, `AI 사용 여부`를 적는다.

개인정보 보호를 위해 실명, 이메일, 개인 연락처는 README와 화면 캡처에 남기지 않는다.

## 순회 지도 우선순위

1. GitHub 로그인·권한·네트워크 문제
2. 저장소를 잘못 clone한 학생
3. `main`에서 수정한 학생의 변경 보존 후 새 브랜치 생성
4. commit은 했지만 push하지 않은 학생
5. push했지만 PR 생성 위치를 못 찾는 학생
6. 빠른 학생의 충돌 확장 과제

## 예상 문제와 대응

| 문제 | 확인 방법 | 수업 중 대응 | 그래도 실패할 때 |
|---|---|---|---|
| GitHub 로그인 불가 | 브라우저 로그인 확인 | 계정 복구보다 실습 흐름 우선, 짝 화면으로 관찰 | 교사 임시 로컬 저장소에서 branch·commit까지 수행 |
| Fork에 Git 실행 파일 미인식 | Fork 설정과 Git 경로 확인 | 내장 Git 선택 또는 앱 재실행 | CLI 가능 학생만 CLI, 나머지는 시범 저장소 사용 |
| clone 권한 오류 | 저장소 URL과 공개/초대 상태 확인 | 올바른 URL 재복사, 초대 수락 | 공개 진단용 저장소 또는 ZIP이 아닌 로컬 repo 제공 |
| `main`에서 수정 | 현재 브랜치와 미커밋 변경 확인 | 변경을 유지한 채 새 브랜치 생성 | 교사가 화면을 보며 순서대로 복구 |
| push 후 PR이 안 보임 | 원격 브랜치 존재 확인 | GitHub의 Compare & pull request 또는 브랜치 선택 | PR URL 직접 생성 안내 |
| 학생별 속도 차이 | 55분 시점 PR 수 확인 | 완료자는 옆 학생에게 답을 대신하지 않고 질문으로 지원 | 충돌 과제는 생략하고 필수 완료 집중 |
